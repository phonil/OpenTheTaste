# API Improvement Workflow

## 0. 목적

이 문서는 API 성능/구조 개선 작업을 너무 무겁지 않게, 그러나 근거 있게 진행하기 위한 기본 절차다.

이 workflow는 아래 상황에서 사용한다.

- 특정 API의 병목을 분석하고 싶을 때
- 구조 개선을 포트폴리오 관점까지 정리하고 싶을 때
- before/after를 숫자로 남기고 싶을 때

---

## 1. 전제

- 전역 규칙은 루트 `AGENTS.md`를 따른다.
- 문서 산출물은 `docs/improvements/{topic}/`에 둔다.
- 한 번에 하나의 API 또는 하나의 개선 주제만 다룬다.
- 측정 없는 주장은 하지 않는다.
- 대안 비교, 측정 결과, 작업 단계는 가능하면 표로 정리한다.

---

## 2. 권장 단계

### P0. 주제 선정

목표

- 왜 이 API를 고르는지 설명 가능한 상태 만들기

해야 할 일

1. 현재 프로젝트 구조 파악
2. 개선 후보 최소 2~3개 도출
3. 후보별 임팩트/난이도/측정 가능성 비교
4. 사용자와 1개 주제 확정

산출물

- topic 폴더 생성
- `001-overview.md` 초안 또는 짧은 메모

---

### P1. As-Is 분석

목표

- 현재 구조와 병목을 숫자로 고정

해야 할 일

1. 요청 흐름 추적
2. 관련 쿼리 확인
3. 현재 구조/문제점 정리
4. 가능하면 부하 테스트 또는 재현 테스트 수행

산출물

- `002-as-is.md`

최소 포함 항목

- 엔드포인트 정보
- 현재 호출 흐름
- 실행 쿼리
- 측정 환경
- 핵심 지표
- 식별된 문제점

---

### P2. 원인 가설

목표

- 증상이 아니라 근본 원인을 정리

해야 할 일

1. 문제마다 가설 2개 이상 세우기
2. 각 가설의 검증 방법 쓰기
3. 검증 후 채택/기각 정리

산출물

- `002-as-is.md` 보강 또는 별도 섹션 추가

---

### P3. 대안 비교와 선택

목표

- 왜 이 방안을 선택했는지 설명 가능하게 만들기

해야 할 일

1. 해결 방안 최소 2개 이상 정리
2. 장점/단점/영향 범위/리스크 비교
3. 사용자 승인으로 최종 방안 선택

산출물

- `003-adr.md`

최소 포함 항목

- Context
- Considered Alternatives
- Decision
- Consequences

---

### P4. 구현

목표

- 승인된 범위만 안전하게 반영

해야 할 일

1. 작업을 작은 단위로 쪼개기
2. 변경 파일 승인받기
3. 테스트 추가 또는 수정
4. 구현
5. 빌드/테스트/로그 확인

산출물

- `004-implementation.md`

최소 포함 항목

- Task Breakdown
- 변경 파일
- 구체적인 구현 포인트
  - 메서드 시그니처
  - 쿼리 형태 또는 알고리즘 구조
  - 레이어별 책임
  - 예외/경계 케이스
- 구현 중 결정
- 테스트 변경 내역

---

### P5. 검증

목표

- 개선 주장을 before/after 수치로 닫기

해야 할 일

1. 가능하면 동일 환경에서 재측정
2. before/after 표 정리
3. 목표 달성 여부 판단
4. 예상과 다른 결과 정리

산출물

- `005-benchmark.md`

최소 포함 항목

- 측정 환경
- 핵심 지표 비교
- 해석
- 재현 방법

---

## 3. 권장 문서 구성

작업이 작으면 아래만 써도 된다.

- `001-overview.md`
- `002-as-is.md`
- `003-adr.md`

구현까지 가면 아래를 추가한다.

- `004-implementation.md`
- `005-benchmark.md`

포트폴리오/회고가 필요할 때만 아래를 추가한다.

- `05-retrospective.md`
- `ai-collaboration.md`

---

## 4. 승인 지점

아래 지점에서는 반드시 사용자 승인 후 진행한다.

1. 주제 확정
2. 측정 방식 확정
3. 근본 원인에 대한 동의
4. 대안 중 최종 선택
5. 수정할 파일 목록 확정
6. 설계 변경 또는 범위 확장

---

## 5. 금지 사항

- 측정 없이 빨라졌다고 쓰지 않는다.
- 대안 없이 바로 구현하지 않는다.
- 승인 없이 파일을 수정하지 않는다.
- 현재 작업 중 새 아이디어를 끼워 넣지 않는다.
- 전체 대화 로그를 문서에 그대로 복붙하지 않는다.

---

## 6. 완료 기준

아래를 만족하면 한 주제가 끝난 것으로 본다.

- 선택 이유가 문서로 남아 있다.
- 변경 이유와 영향 범위를 설명할 수 있다.
- 검증 명령과 결과가 기록되어 있다.
- 남은 리스크와 다음 액션이 정리되어 있다.
